# Synchronization

Each enabled mapping owns one dedicated AutoPhish target list. The app reads the complete Nextcloud group and every destination page before writing. Destination reads are bounded to 1,000 pages and each synchronization run has a five-minute operation deadline. Lists too large to read within these limits fail safely rather than treating truncated results as complete. Active users with a valid primary email are matched using trim/lowercase normalization; disabled users are excluded. Display names are sent as `firstName` (maximum 100 characters), without inventing a last name. Existing canonical names are never updated. No Nextcloud user IDs or group attributes are sent to AutoPhish.

Missing and invalid emails are skipped. Duplicate normalized emails are added once. Both conditions block removals because the source is ambiguous; the administrator sees counts and a partial result. A successfully read empty group can clear its dedicated list. Missing groups, backend read failures, incomplete destination reads, malformed memberships, failed additions and unverified additions prevent destructive reconciliation for that mapping.

Missing members are added in batches of at most 200 and below the API payload limit. After additions, the app rereads the complete destination to verify that required memberships exist. Only then does it delete stale memberships, using IDs returned by that list and the list-specific removal endpoint. It never deletes company-wide target identities or replaces other list memberships. Already absent memberships are harmless. A failure during removals can leave some memberships removed; the next run converges without a rollback.

Background cron, `occ integration_autophish:sync` and administrator configuration writes share a small owner lease in Nextcloud’s existing app configuration database. Concurrent runs return a safe skipped result. The lease expires after ten minutes so a crashed process does not block work permanently; an old owner cannot release a newer owner’s lease. A five-minute monotonic operation deadline and fresh database reads of revision/ownership (bypassing process caches) precede HTTP attempts, mutations and status writes. App disable or removal cancels a running operation after any in-flight request finishes. Atomic conditional local writes cannot recreate removed configuration or overwrite a newer owner’s status. Multiple application nodes must share the Nextcloud database and keep their clocks synchronized. Scheduling is bounded to 5 minutes–24 hours and depends on Nextcloud cron execution.

Status stores only timestamps, counts and safe messages. The last successful timestamp is retained across failed or partial runs. Status is persisted as running before work and after each completed mutation; a stopped process leaves an unfinished running result. Completed mutation counts are retained even when a later operation fails. A storage failure stops further writes. A process killed between a remote mutation and local status persistence can leave counts slightly behind; the next run reconciles the actual memberships. A deadline-limited run records a safe cancellation result only if its original revision and owner lease remain current. Lifecycle cancellation does not write local state. An interrupted running status may remain until the next run. No email addresses, user IDs, API keys or provider response bodies are stored in status or logged by the synchronization runner.
